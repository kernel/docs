**status:** <Badge color="yellow">preview</Badge>

reaching a bot-protected site is usually trial and error. an agent gets
silently blocked, and you spend sessions and tokens rediscovering which proxy
type and stealth settings actually load the page. every team repeats that
search for the same sites.

the <span className="kernel-brand-name">KERNEL</span> config registry replaces
the search with an answer. submit a url and
<span className="kernel-brand-name">KERNEL</span> returns the browser and proxy
configuration it recommends for that site, with the evidence behind it: how
often the configuration got in, how many trials that's based on, and when it
was last verified. when <span className="kernel-brand-name">KERNEL</span> hasn't
seen a site, it runs an analysis against the live site and records what worked.

recommendations are advisory. you review and apply them yourself, and
<span className="kernel-brand-name">KERNEL</span> never changes your sessions
or creates resources on your behalf.

<Note>
  the config registry is in preview. it's enabled per organization for
  hobbyist plans and up, and available in the dashboard under **Browsers**, in
  the api, and in the sdks. a recommendation covers browser settings and a
  <span className="kernel-brand-name">KERNEL</span> proxy recipe. it doesn't
  tell your agent how to complete a task on the site; for the wider picture on
  getting through, start with the
  [bot detection overview](/browsers/bot-detection/overview).
</Note>

## How the config registry works

### Knowledge is keyed on the exact url

a target is identified by scheme, host, port, and path. the query string and
fragment are used when <span className="kernel-brand-name">KERNEL</span>
navigates to the site, but not to identify it, so
`https://www.kernel.sh/docs?ref=a` and `https://www.kernel.sh/docs` share one
record. urls can be up to 2,048 characters and must be public http or https.

when the exact url is unknown, <span className="kernel-brand-name">KERNEL</span>
falls back to what it knows about the host, then the registrable domain. the
response says which one you got in `match_scope`, so a recommendation for
`kernel.sh` is never mistaken for one about `/docs`.

### Lookups read, analyses write

`lookup` is side-effect free. it answers instantly from current knowledge and
never starts work.

<CodeGroup>

```typescript TypeScript
const result = await kernel.configRegistry.lookup({
  url: 'https://www.kernel.sh/docs',
});

if (result.recommendation?.type === 'recommendation') {
  console.log(result.recommendation.browser, result.recommendation.proxy);
}
```

```python Python
result = kernel.config_registry.lookup(url="https://www.kernel.sh/docs")

if result.recommendation and result.recommendation.type == "recommendation":
    print(result.recommendation.browser, result.recommendation.proxy)
```

</CodeGroup>

`resolve` starts an analysis for the url in your project, or joins the one
already running, and returns an `analysis` to poll. it always responds `202`
with a null recommendation; the result arrives on the analysis, not on the
resolve call.

<CodeGroup>

```typescript TypeScript
const started = await kernel.configRegistry.resolve({
  url: 'https://www.kernel.sh/docs',
});

let result = started;
while (result.analysis?.status === 'running') {
  await new Promise((resolve) => setTimeout(resolve, 5000));
  result = await kernel.configRegistry.analyses.retrieve(started.analysis.id);
}

console.log(result.analysis?.status, result.recommendation);
```

```python Python
import time

started = kernel.config_registry.resolve(url="https://www.kernel.sh/docs")

result = started
while result.analysis and result.analysis.status == "running":
    time.sleep(5)
    result = kernel.config_registry.analyses.retrieve(started.analysis.id)

print(result.analysis.status, result.recommendation)
```

</CodeGroup>

a finished analysis reports what that run concluded. later analyses of the
same site don't rewrite it, so an analysis id is a stable record you can link
to or audit. `lookup`, by contrast, always reflects the newest knowledge.

analyses, proxies, and browsers are project-scoped. select a project on the sdk
client or use a project-scoped api key; otherwise
<span className="kernel-brand-name">KERNEL</span> uses your organization's
default project.

### Evidence decides what's recommended

a recommendation carries `verification` and `evidence`, and together they tell
you how much to trust it.

| field                                                    | behavior                                                                                                  |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `verification: "verified"`                               | the exact url met the bar: at least 3 conclusive trials, with 80% or more of them getting in              |
| `verification: "inferred"`                               | derived from host or domain knowledge; test it against your workflow before relying on it                  |
| `evidence.success_rate`                                  | accessed trials over conclusive trials; inconclusive trials are excluded                                   |
| `evidence.sample_size`, `evidence.run_count`             | how many conclusive trials, across how many analyses                                                       |
| `evidence.last_verified_at`, `evidence.last_observed_at` | when the configuration last met the bar, and when it was last tested at all                                |

when several configurations perform equally well, the recommendation is the
one <span className="kernel-brand-name">KERNEL</span> ranks first, and the rest
are returned in `working_configurations` with the recommendation first. stealth
wins ties.

knowledge that hasn't been observed for 90 days ages out, and analysis history
is retained for 90 days. a site nobody has analyzed recently can go back to
returning nothing.

### Analysis runs against the live site

an analysis loads the url repeatedly in real
<span className="kernel-brand-name">KERNEL</span> browsers across proxy types
and stealth settings, and judges the resulting page screenshots. it takes
several minutes. `analysis.expires_at` is the deadline after which a
still-running analysis is marked `expired`. one analysis runs per url per
project at a time, and a second `resolve` joins it rather than starting another.

<Warning>
  only submit public urls you're authorized to test. don't include secrets,
  session tokens, signed links, private data, or urls where a get request
  triggers an action.
</Warning>

by default <span className="kernel-brand-name">KERNEL</span> chooses proxy exit
countries itself, starting with the united states. pass
`allowed_proxy_countries` with up to 10 iso 3166 codes to restrict where a
recommended proxy may exit. on `resolve` it limits what gets tested, and
<span className="kernel-brand-name">KERNEL</span> may test a subset; on `lookup`
it limits which knowledge comes back.

some protections only appear once a session interacts with the site. pass an
`intent`, a sentence describing the workload you'll run, and the analysis
drives a browser toward it after the configuration trials. the response
reports how far it got in `workload_outcome`, and whatever it observed feeds
the guidance described below. intent requires an https url, and a `resolve`
that reaches an analysis already running with a different intent returns `409`
naming the analysis to poll.

<CodeGroup>

```typescript TypeScript
const started = await kernel.configRegistry.resolve({
  url: 'https://www.kernel.sh/docs',
  intent: 'search the docs for proxies and open the first result',
  allowed_proxy_countries: ['US', 'GB'],
});
```

```python Python
started = kernel.config_registry.resolve(
    url="https://www.kernel.sh/docs",
    intent="search the docs for proxies and open the first result",
    allowed_proxy_countries=["US", "GB"],
)
```

</CodeGroup>

## Evaluating a recommendation

read `recommendation.type` first. it's either a `recommendation` or a
`no_recommendation` with a reason:

| code                       | meaning                                                                                                                                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `proxy_restricted`         | <span className="kernel-brand-name">KERNEL</span>'s proxy network can't reach this site. see [restricted destinations](/acceptable-use#proxy-fair-use) and consider a [custom proxy](/proxies/custom) |
| `no_working_configuration` | the analysis finished and no configuration reliably got in                                                                                                                                                       |
| `inconclusive`             | every trial was inconclusive, so <span className="kernel-brand-name">KERNEL</span> couldn't judge whether the site let the browser in                                                                            |

`lookup` reports `proxy_restricted` from stored knowledge but is otherwise null
whenever it has nothing usable, whether because nobody has analyzed the site or
because nothing worked. a null from `lookup` means run `resolve`, not that the
site is unreachable.

then read the evidence. `verified` with a recent `last_verified_at` and a
sample size you're comfortable with is ready to use. `inferred`, an old
`last_verified_at`, or a small sample means run your own check or refresh the
analysis. re-run when the evidence is older than your risk tolerance, with
**Refresh analysis** in the dashboard or another `resolve`.

`guidance`, when present, is short markdown about the anti-bot protections
observed on the site and how to navigate them. it's assembled from what the
analysis saw and from <span className="kernel-brand-name">KERNEL</span>'s notes
on those vendors, and it's returned even when no configuration got in. it's
advisory and not verified against your workflow, so treat it as a starting
point for your agent's instructions rather than a rule.

## Applying a recommendation

`recommendation.browser` passes straight into browser creation: `stealth`,
`headless`, `gpu`, and `viewport`. `recommendation.proxy` is one of two
recipes.

| `proxy.mode` | behavior                                                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `direct`     | no <span className="kernel-brand-name">KERNEL</span> proxy resource is needed. pass `{ mode: "direct" }` as the browser's `proxy`. this must be explicit on a stealth browser, which otherwise picks up the default stealth proxy |
| `managed`    | `proxy.create` is a ready proxy creation payload. create the proxy once, keep its id, and pass `{ id }` as the browser's `proxy` for every session                                                 |

<CodeGroup>

```typescript TypeScript
const { recommendation } = await kernel.configRegistry.lookup({
  url: 'https://www.kernel.sh/docs',
});
if (recommendation?.type !== 'recommendation') {
  throw new Error('no recommendation yet');
}

// once, at setup time. store proxy.id and reuse it.
const proxy =
  recommendation.proxy.mode === 'managed'
    ? await kernel.proxies.create(recommendation.proxy.create)
    : null;

// every session
const browser = await kernel.browsers.create({
  ...recommendation.browser,
  proxy: proxy ? { id: proxy.id } : { mode: 'direct' },
});
```

```python Python
result = kernel.config_registry.lookup(url="https://www.kernel.sh/docs")
recommendation = result.recommendation
if not recommendation or recommendation.type != "recommendation":
    raise RuntimeError("no recommendation yet")

# once, at setup time. store proxy.id and reuse it.
proxy = None
if recommendation.proxy.mode == "managed":
    proxy = kernel.proxies.create(
        **recommendation.proxy.create.model_dump(exclude_none=True)
    )

# every session
browser = kernel.browsers.create(
    **recommendation.browser.model_dump(),
    proxy={"id": proxy.id} if proxy else {"mode": "direct"},
)
```

</CodeGroup>

proxy creation isn't idempotent, so don't create one per session. key the
stored proxy id by the full `proxy.create` recipe and create a replacement only
when the recipe changes. the proxy and the browser must belong to the same
project.

the dashboard generates these recipes for every recommendation in typescript,
python, and cli, including only the settings that differ from
<span className="kernel-brand-name">KERNEL</span>'s defaults. a recommendation
that matches the defaults renders as a plain browser create call.

see the [config registry api reference](https://kernel.sh/docs/api-reference/config-registry/look-up-a-config)
for endpoints and complete request and response schemas.
