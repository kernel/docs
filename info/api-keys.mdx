An API key is the credential your server, script, or CI job uses to call Kernel without an interactive login. Treat it like a password: keep it out of client-side code, store it in a secret manager, and rotate it when access changes.

Kernel only returns the plaintext key once, when you create it. Save the `key` value immediately. After that, Kernel only shows the masked value.

<Tip>
**For anything that isn't a person at a keyboard, use [workload identity federation](/info/workload-identity/overview) instead of an API key.** An API key is a stored secret that works until someone revokes it. With federation, a CI job, cloud service, or Kubernetes pod exchanges a token from its own identity provider for a short-lived KERNEL access token, and there's no secret to store. API keys remain the right tool for local development and for environments with no identity provider. See [API authentication](/info/authentication) to choose.
</Tip>

## Before you start

You need one existing Kernel credential to create another API key:

- Set `KERNEL_API_KEY` before running the SDK examples.

API keys can be **org** or **project** scoped:

- Omit `project_id` to create an org-scoped key that can access resources across your organization.
- Set `project_id` to create a project-scoped key that can only access resources in that project.
- When you authenticate with a project-scoped key, you can only create another project-scoped key for the same project.

Organization/project scope sets the key's boundary. A `policy` separately limits which actions and resources it can access inside that boundary. Both organization- and project-scoped keys can have policies.

## Create an API key

Use the SDKs when your backend needs to provision keys for environments, customers, or automation jobs.

### SDKs

## Scope a key to specific resources

A personal API key without a policy is unrestricted within its organization or project. Add a `policy` when you create a key to limit what it can do. Keys created without `policy` work exactly as before.

Use scoped keys when you hand a credential to code you trust less than your backend, such as an AI agent or a short-lived job.

### How policies work

A policy is a list of **statements**. Each statement allows one **action** on one **resource**, and the key is denied everything no statement allows.

- A **resource** selects one project-owned object, such as `projects/{project_id}/extensions/{extension_id}`, an organization-owned object, such as `credential_providers/{provider_id}`, or a container such as `projects/{project_id}/*` or `organizations/{org_id}/*`.
- An **action** is an exact name such as `browsers:use`, `extensions:read`, or `api_keys:create`. A container wildcard grants that action throughout the container, not every action. To grant several actions at once, see [action wildcards](/info/api-key-permissions#action-wildcards).

A statement can also carry a **condition** that narrows it to matching requests. A condition names a request attribute, a comparison operator, and that operator's values. See [Limit a key to your IP ranges](/info/api-keys#limit-a-key-to-your-ip-ranges).

Some operations need more than one action. For example, creating a browser with a profile needs `browsers:create` and `browsers:use` on the project, plus `profiles:use` on that profile. See [API key permissions](/info/api-key-permissions) for every action and what each operation requires.

Policies cover browsers, profiles, vaults, proxies, extensions, telemetry destinations, browser pools, tasks and reports, apps, managed auth, credentials, organization/project administration, API keys, audit logs, and the configuration registry. Start with a [policy example](/info/api-key-policy-examples) for your workload.

### Create a scoped key

This key can create and control browsers in one project, only with profile `prof_7h2kq9x4m1` or no profile, and expires in one hour:

<CodeGroup>
```typescript TypeScript
import Kernel from '@onkernel/sdk';

const kernel = new Kernel({
  apiKey: process.env.KERNEL_API_KEY,
});

const apiKey = await kernel.apiKeys.create({
  name: 'checkout-agent-run-4812',
  project_id: 'proj_staging_9f3k',
  expires_at: new Date(Date.now() + 60 * 60 * 1000).toISOString(),
  policy: {
    statements: [
      { action: 'browsers:create', resource: 'projects/proj_staging_9f3k/*' },
      { action: 'browsers:use', resource: 'projects/proj_staging_9f3k/*' },
      { action: 'profiles:use', resource: 'projects/proj_staging_9f3k/profiles/prof_7h2kq9x4m1' },
    ],
  },
});

console.log(apiKey.key); // Save this value now. Kernel won't show it again.
```

```python Python
import os
from datetime import datetime, timedelta, timezone

from kernel import Kernel

client = Kernel(api_key=os.environ["KERNEL_API_KEY"])

api_key = client.api_keys.create(
    name="checkout-agent-run-4812",
    project_id="proj_staging_9f3k",
    expires_at=datetime.now(timezone.utc) + timedelta(hours=1),
    policy={
        "statements": [
            {"action": "browsers:create", "resource": "projects/proj_staging_9f3k/*"},
            {"action": "browsers:use", "resource": "projects/proj_staging_9f3k/*"},
            {"action": "profiles:use", "resource": "projects/proj_staging_9f3k/profiles/prof_7h2kq9x4m1"},
        ],
    },
)

print(api_key.key)  # Save this value now. Kernel won't show it again.
```
</CodeGroup>

### Expiry and revocation

- Use `expires_at` instead of `days_to_expire` for an exact expiry. When creating a key with a policy, follow the [issuer expiry rule](#delegate-a-narrower-key).
- Expired and deleted keys can't authenticate new API requests.
- Deleting a key through the API or dashboard, or rotating it with `expire_in_days: 0`, also ends browser sessions associated with that key, including pool browsers it acquired and hasn't released. Cleanup runs asynchronously and discards unsaved profile changes.
- Grace-period expiry and natural expiry do **not** end existing browsers. Delete those browsers explicitly if you need to stop them.
- Connection URLs (CDP, WebDriver, live view) stop working when their browser ends, not when the key stops authenticating.
- If browser cleanup can't be scheduled, deletion or immediate rotation fails without committing the key change.
- Rotating a scoped key keeps its policy.

<Note>
Automatic cleanup only covers browsers associated with the key. Some browsers created before this behavior was introduced may not have that association. Delete those browsers directly. Cleanup doesn't undo profile changes you've already saved, delete browser pools, or stop app invocations or deployments.
</Note>

### Delegate a narrower key

You can use a scoped key to create another scoped key:

1. Grant the issuer `api_keys:create` on the new key's project or organization container.
2. Supply a `policy` whose statements are covered by the issuer's policy, and keep the new key inside the issuer's organization/project boundary.
3. If the issuer expires, set the child's expiry no later than the issuer's. To issue a longer-lived child, the issuer needs `api_keys:issue_beyond_expiry` on the new key's container and must request a finite lifetime of at most 3650 days. Kernel returns `400` rather than shortening a disallowed lifetime. When rotating with a scoped key, the same expiry rule applies, but Kernel checks the permission on the existing key.

For example, an issuer with `api_keys:create` and `browsers:use` on a project can issue a key with only `browsers:use` on one browser in that project. Use the same SDK creation call shown above with the narrower policy.

Use `api_keys:read` to inspect keys, `api_keys:write` to rename them, `api_keys:delete` to revoke them, and `api_keys:rotate` to replace them. Grant these actions separately from key issuance.

### Allow longer-lived child keys

Use an unscoped credential to issue a trusted key with `api_keys:issue_beyond_expiry`. This permission doesn't grant creation, rotation, or resource access by itself.

<CodeGroup>
```typescript TypeScript
const issuer = await kernel.apiKeys.create({
  name: 'ci-key-issuer',
  project_id: 'proj_staging_9f3k',
  days_to_expire: 30,
  policy: {
    statements: [
      { action: 'api_keys:create', resource: 'projects/proj_staging_9f3k/*' },
      { action: 'api_keys:issue_beyond_expiry', resource: 'projects/proj_staging_9f3k/*' },
      { action: 'browsers:use', resource: 'projects/proj_staging_9f3k/*' },
    ],
  },
});
```

```python Python
issuer = client.api_keys.create(
    name="ci-key-issuer",
    project_id="proj_staging_9f3k",
    days_to_expire=30,
    policy={
        "statements": [
            {"action": "api_keys:create", "resource": "projects/proj_staging_9f3k/*"},
            {"action": "api_keys:issue_beyond_expiry", "resource": "projects/proj_staging_9f3k/*"},
            {"action": "browsers:use", "resource": "projects/proj_staging_9f3k/*"},
        ],
    },
)
```
</CodeGroup>

Authenticate with `issuer.key` to create a child with `days_to_expire: 365` and only `browsers:use` on this project. Its expiry is one year, not silently shortened to the issuer's 30 days. Without the special permission, that request returns `400`.

Scoped callers cannot create or rotate keys whose policies contain `api_keys:issue_beyond_expiry`, so the child can't inherit this authority. Add `api_keys:rotate` separately to let the issuer rotate other keys.

<Warning>
Grant this permission only to trusted issuers. Their child keys can remain valid after the issuer expires or is revoked.
</Warning>

## Limit a key to your IP ranges

Add a `condition` to a statement to restrict where requests can come from. The `source_ip` condition allows the statement only when the request's client address is inside one of its CIDR networks:

```json
{
  "statements": [
    {
      "action": "browsers:use",
      "resource": "projects/proj_staging_9f3k/*",
      "condition": {
        "key": "source_ip",
        "operator": "in",
        "values": ["203.0.113.0/24", "2001:db8::/32"]
      }
    }
  ]
}
```

Use this when a key is pinned to a fixed egress: if the key leaks into a log, a repository, or a third-party tool, requests from anywhere else get `403` before they touch your data.

How conditions evaluate:

- Each entry in `values` must be a CIDR network (`203.0.113.0/24`). A bare address without a mask, an entry with host bits set, and an IPv4 network written in IPv6 notation are rejected with `400` at creation—so a mistyped mask can't silently grant a whole block.
- Requests from outside every listed network get `403` with `insufficient_scope`, and the denial is recorded in your [audit logs](/info/audit-logs) with the client IP, so you can widen the list from evidence.
- A condition only narrows its own statement. If you want a key that only works from your network, add the same condition to every statement in its policy.
- Kernel evaluates the address the trusted edge proxy reports, not a client-supplied header value, so a request can't spoof its way in.

### Add an IP allowlist to an existing key

You don't need to rotate a key to add, change, or remove IP rules. Update the key with a `policy`, and the credential, name, project, and expiry stay the same—your consumers keep the same secret:

<CodeGroup>
```typescript TypeScript
await kernel.apiKeys.update('key_01jwv4tn5m8k3q2v7x9p0a1bc2', {
  policy: {
    statements: [
      {
        action: 'browsers:use',
        resource: 'projects/proj_staging_9f3k/*',
        condition: { key: 'source_ip', operator: 'in', values: ['203.0.113.0/24'] },
      },
    ],
  },
});
```

```python Python
client.api_keys.update(
    "key_01jwv4tn5m8k3q2v7x9p0a1bc2",
    policy={
        "statements": [
            {
                "action": "browsers:use",
                "resource": "projects/proj_staging_9f3k/*",
                "condition": {"key": "source_ip", "operator": "in", "values": ["203.0.113.0/24"]},
            }
        ],
    },
)
```
</CodeGroup>

To change permissions with a scoped key, you need `api_keys:set_policy` on the target key. You must cover both its current and replacement policies; you can’t convert an unrestricted key this way. To change its name in the same request, you also need `api_keys:write`.

Updating `policy` **fully replaces** the key's permissions, so send the complete policy, not just the statements you're changing. The new policy takes effect within the authorization cache (~10 seconds) and applies only to new requests—already-open browser connections keep running.

Attaching a policy to a key that doesn't have one makes the key scoped: every action and resource the policy doesn't list is denied. There's no way to remove a policy from a key and go back to unrestricted—if you no longer need a scoped key, delete it.

<Note>
A key used through a hosted MCP server is evaluated against the MCP server's egress address, so an IP-restricted key is denied everywhere until MCP support ships. If you route keys through a hosted MCP server, leave `source_ip` conditions off those keys for now.
</Note>

## App runtime policy

An app’s runtime policy controls which Kernel API calls that version can make. Set it when you deploy. Your app keeps those permissions if the key you used to deploy expires or is revoked; you don’t need to redeploy or store a key for the app.

**Default:** When you deploy with a scoped key and omit `runtime_policy`, the app gets only `invocations:write` on `projects/{project_id}/*` so it can report results. That grant lets the app update other apps’ invocations in the same project. Put apps that don’t trust each other in separate projects.

**To grant more access**, send `runtime_policy` as a JSON form field on `POST /deployments`. The SDKs don't accept `runtime_policy` yet, so these examples call the API directly. Set `KERNEL_PROJECT_ID` to your project ID and `KERNEL_API_KEY` to your deploying key, and put `main.py` and its dependency manifest at the root of `app.zip`:

<CodeGroup>
```typescript TypeScript
import { readFile } from 'node:fs/promises';

const projectId = process.env.KERNEL_PROJECT_ID!;
const resource = `projects/${projectId}/*`;
const runtimePolicy = {
  statements: [
    { action: 'invocations:write', resource },
    { action: 'browsers:create', resource },
    { action: 'browsers:use', resource },
  ],
};

const form = new FormData();
form.append('file', new Blob([await readFile('app.zip')]), 'app.zip');
form.append('entrypoint_rel_path', 'main.py');
form.append('runtime_policy', JSON.stringify(runtimePolicy));

const response = await fetch('https://api.onkernel.com/deployments', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${process.env.KERNEL_API_KEY}`,
    'X-Kernel-Project-Id': projectId,
  },
  body: form,
});
if (!response.ok) throw new Error(`${response.status}: ${await response.text()}`);
console.log(await response.json());
```

```python Python
import json
import os

import httpx

project_id = os.environ["KERNEL_PROJECT_ID"]
resource = f"projects/{project_id}/*"
runtime_policy = {
    "statements": [
        {"action": "invocations:write", "resource": resource},
        {"action": "browsers:create", "resource": resource},
        {"action": "browsers:use", "resource": resource},
    ]
}

with open("app.zip", "rb") as app:
    response = httpx.post(
        "https://api.onkernel.com/deployments",
        headers={
            "Authorization": f"Bearer {os.environ['KERNEL_API_KEY']}",
            "X-Kernel-Project-Id": project_id,
        },
        files={"file": ("app.zip", app, "application/zip")},
        data={
            "entrypoint_rel_path": "main.py",
            "runtime_policy": json.dumps(runtime_policy),
        },
        timeout=120,
    )
response.raise_for_status()
print(response.json())
```
</CodeGroup>

This app can report results and create browsers without attachments. Include the unconditional project-wide `invocations:write` grant and any additional permissions your app needs. The policy must fit within the app’s project and your own permissions, reference existing resources, and exclude `api_keys:issue_beyond_expiry`.

To deploy with a scoped key, grant it container-wide `deployments:create`, `deployments:delete`, and `invocations:write`, plus any additional permissions in the app’s policy. To run the app with a scoped key, grant it `invocations:create` on the container and every permission in the app’s policy.

Kernel supplies a short-lived `KERNEL_API_KEY` with the app’s permissions for each run. Moving a deployment to another host preserves the policy. Stopping it prevents new runs; it doesn't revoke keys already issued. `KERNEL_API_KEY` is a [reserved environment variable](/apps/deploy#reserved-environment-variables). To supply a credential for your own API calls, pass it under another name.

See the [app policy example](/info/api-key-policy-examples) for separate deployer, runtime, and invoker permissions.

### Existing deployments

<Warning>
Scoped callers can't invoke an app that runs with an unrestricted shared key, even with `invocations:create`. To let them run it, redeploy with an explicit runtime policy that their permissions cover.
</Warning>

Deploying with an unrestricted credential and omitting `runtime_policy` creates a shared key; it doesn't migrate the app to per-invocation keys. If the shared key has a policy, it must be live, its permissions must be covered by the caller, and it must expire no later than the caller. Host moves preserve these rules; superseded deployments keep their shared key until in-flight runs drain.

## List and inspect API keys

Use `GET /org/api_keys` to list keys and `GET /org/api_keys/{id}` to inspect one. List and retrieve responses include `masked_key`, `project_id`, `project_name`, `created_by`, expiry metadata, and `policy` for scoped keys, but they don't include the plaintext key. If `policy` is absent, the key is unrestricted within its project or organization.

The list returns `active` keys by default: keys that are neither deleted nor expired. Pass `status` to see the others, and combine these filters to narrow the list:

| Query parameter | Returns |
| --- | --- |
| `status` | `active` (the default), `expired`, `deleted`, or `all`. Expired keys aren't part of `active`. |
| `principal_type` | `user` for keys that act as a person, or `service_account` for keys that act as a [service account](/info/workload-identity/service-accounts). |
| `service_account_id` | Keys that belong to one service account. |
| `created_by` | Keys created by one user ID. |
| `project_id` | Keys scoped to one project. Use `org` for keys that aren't scoped to a project. |

In the dashboard, filter the list by **Created by**, **Linked account**, and **Project**, and switch between **Active**, **Expired**, and **Deleted**.

<CodeGroup>
```typescript TypeScript
for await (const apiKey of kernel.apiKeys.list({ limit: 20 })) {

const apiKey = await kernel.apiKeys.retrieve('key_01jwv4tn5m8k3q2v7x9p0a1bc2');

```

## Rename, update permissions, or delete an API key

Rename a key when the owner or purpose changes. Update its `policy` to add, change, or remove IP rules and permissions without rotating the credential. Delete a key when the workload no longer needs access.

<Warning>
An API key cannot delete itself. Authenticate with a different key when deleting a key, so the request cannot revoke the credential that is authorizing it. A deleted key stops authenticating new requests within the authorization cache (~10 seconds). Deleting a key also ends its associated browsers asynchronously and discards their unsaved profile changes.
</Warning>

<CodeGroup>
```typescript TypeScript
await kernel.apiKeys.update('key_01jwv4tn5m8k3q2v7x9p0a1bc2', {
  name: 'staging-ci-rotated',
});

await kernel.apiKeys.delete('key_01jwv4tn5m8k3q2v7x9p0a1bc2');
```

```python Python
import os

client = Kernel(api_key=os.environ["KERNEL_API_KEY"])
```

## Rotate a key

`rotate` issues a replacement key in a single call and keeps the old key working for a short grace period, so your workload can switch over without downtime. The new key copies the rotated key's name, project scope, and policy, and—like create—Kernel returns the plaintext `key` only once.

Two optional parameters control the timing:

- `days_to_expire` sets the new key's lifetime in days (`1`-`3650`). Omit it to give the new key the same lifetime the rotated key originally had, or to never expire if the old key never did.
- `expire_in_days` sets how long the old key keeps working before it expires. Use `0` to revoke it immediately, or omit it for the default 7-day grace window. The old key stops authenticating automatically once the window passes—you don't need to delete it.

If the key you rotate with has no policy, these lifetime rules apply to every target, including keys with policies, and you don't need `api_keys:issue_beyond_expiry`.

If the key you rotate with has a policy, it needs `api_keys:rotate` on the target and must cover the target's policy. The [issuer expiry rule](#delegate-a-narrower-key) applies even when you omit `days_to_expire` and reuse the old lifetime. A scoped caller can't rotate a key that itself carries `api_keys:issue_beyond_expiry`.

<CodeGroup>
```typescript TypeScript
const rotated = await kernel.apiKeys.rotate('key_01jwv4tn5m8k3q2v7x9p0a1bc2', {
  days_to_expire: 30,
  expire_in_days: 7,
});

console.log(rotated.key); // Save this value now. Kernel won't show it again.
console.log(rotated.id, rotated.masked_key);
```

```python Python
import os
from kernel import Kernel

client = Kernel(api_key=os.environ["KERNEL_API_KEY"])

rotated = client.api_keys.rotate(
```

After you rotate a key:

1. Store the new plaintext key in your secret manager.
2. Deploy or restart the workload that uses `KERNEL_API_KEY`.
3. Verify the workload can call Kernel before the grace window ends.

To cut over immediately instead of using a grace window, pass `expire_in_days: 0`. The old key stops working, its associated browsers are ended asynchronously, and unsaved profile changes in those browsers are discarded. With a grace period, existing browsers keep running after the old key expires.

## Service account API keys

A key you create for yourself acts as you. For a workload that can't use [workload identity federation](/info/workload-identity/overview), an organization admin can link a key to a [service account](/info/workload-identity/service-accounts) instead, so the key belongs to the organization and keeps working when its creator leaves.

A service account API key always has one project and an explicit policy, and it can't hold API key permissions. Create one from the dashboard: click **Create API Key**, choose **Continue with an API key**, and pick the service account under **Linked account**. See [Service account API keys](/info/workload-identity/service-accounts#service-account-api-keys).

It's still a stored secret. Prefer federation wherever your workload has an identity provider, and [move existing workloads](/info/workload-identity/migrate-from-api-keys) when you can.

## Troubleshooting

| Error | What it means | What to do |
| --- | --- | --- |
| `400 Bad Request` | The name is missing, `days_to_expire` is outside `1`-`3650`, `expire_in_days` is outside `0`-`3650`, or `project_id` is empty. | Send a name, choose a valid expiry, or omit `project_id` for an org-scoped key. |
| `400 Bad Request` (rotate) | `days_to_expire` is shorter than `expire_in_days`, so the new key would expire before the old key's grace window ends. | Raise `days_to_expire` or lower `expire_in_days`. |
| `400 Bad Request` (policy) | The action, resource, or condition is invalid, or the update sets `policy: null`. | For `source_ip`, use CIDR notation without host bits or IPv4-in-IPv6 addresses. Check the [permission reference](/info/api-key-permissions) and send the complete replacement policy. |
| `400 Bad Request` (issuer expiry) | The requested lifetime exceeds what the issuer can grant. | Check the [issuer expiry rule](#delegate-a-narrower-key). |
| `401 Unauthorized` | Kernel couldn't authenticate the request. | Set a valid `KERNEL_API_KEY`. |
| `403 Forbidden` (`insufficient_scope`) | A scoped key is missing a permission. | The message names the missing action and resource. Add it to the policy. |
| `404 Not Found` | The project, API key, or a resource named in the policy doesn't exist, or the caller can't access it. | Check the ID. If you're using a project-scoped key, you can only rotate keys in that same project. |
