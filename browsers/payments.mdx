your browser agent can complete purchases with KERNEL while your application keeps control of what gets bought and when the user approves it. the agent never sees raw card details, and neither does your application's injection code or the model's context.

KERNEL gives you two ways to pay: collect the user's card with KERNEL hosted payments, or connect a wallet the user already has through a third-party integration such as link by stripe, shop pay, or agentcard.

KERNEL hosted payments is the recommended approach if you want to own the card collection and approval experience inside your product. a third-party wallet is preferred if your users already have one, or if you'd like the provider to approve each purchase and issue the credential that pays.

| | KERNEL hosted payments | third-party wallets |
| --- | --- | --- |
| **what the user needs** | any card they want to pay with | an account with the provider: link, shop, or agentcard |
| **onboarding** | the user enters a card on a KERNEL-hosted page or in an embedded component on your domain | the user signs in to or enrolls with the provider and connects it to your application |
| **who approves each purchase** | your application, plus a card verification step for some cards | the provider, in its own app or approval page |
| **what pays at checkout** | for eligible cards, a network token for the user's existing card | link and shop pay issue a credential for the approved purchase; agentcard pays on the user's behalf after approval |
| **checkout coverage** | any checkout with a card form | depends on the provider; see [choose a third-party wallet](#choose-a-third-party-wallet) |
| **testing** | live only | live only, except agentcard, which also has a sandbox |

## Common use cases

### Use KERNEL hosted payments

- you want card entry and purchase confirmation to look and feel like your product.
- your users don't have, or don't want to create, an account with a wallet provider.
- a user needs to keep several cards on file and pick which one pays for each purchase, where [multiple cards](/integrations/wallets/pay-with-multiple-cards) are enabled.

one common use case is a shopping assistant inside your app. the user adds a card once during onboarding, on your own page with [embedded card capture](/integrations/wallets/embedded-card-capture). when the agent reaches checkout, your application confirms the order with the user and KERNEL fills the payment fields. the user never leaves your product.

### Use a third-party wallet

- your users already pay with link, shop pay, or agentcard and trust that brand with their cards.
- you want the provider to ask the user to approve each purchase, instead of building that step yourself.
- you want to limit what's in the browser at checkout: link and shop pay issue a card or token for one approved purchase, and agentcard keeps the card out of the browser entirely.

one common use case is a consumer agent that books or buys on the user's behalf across many sites. the user connects their link wallet once. for each purchase, link sends the user an approval request and issues a one-time credential, and KERNEL fills it into the checkout.

## Choose a third-party wallet

| wallet | best when | limits |
| --- | --- | --- |
| [link by stripe](/integrations/wallets/stripe-link) | your users already have link, or the merchants use stripe checkout. on supported stripe checkouts, link pays without card fields | users need a us phone number |
| [shop pay](/integrations/wallets/shop-pay) | your users keep cards saved in their shop account. the card it issues works on any checkout with a card form, not only shopify stores | usd purchases only. prefer a site's own agent checkout when it has one, and don't fall back to shop pay after another payment method fails |
| [agentcard](/integrations/wallets/agentcard) | you need a sandbox to build and test against, or you want approval rules the user sets in agentcard | the merchant's payment processor must be [one KERNEL recognizes](/integrations/wallets/agentcard#checkout-and-processor-coverage) |

need a wallet that isn't listed? [contact support](/info/support).

## What every approach shares

- **payment values stay out of your code and the model.** KERNEL's [`fill` api](/vaults/fill) writes payment values into the browser and returns only the outcome. agentcard goes further: the agent enters placeholder values, and the real card never enters the browser.
- **your application stays in control.** verify the merchant, items, amount, and currency before you authorize a purchase. show connection and approval links to the user in your own trusted interface, never to the agent.
- **the merchant decides whether the payment succeeded.** a completed fill or approval isn't proof of payment. check the merchant's order record before you report success.

<Warning>
  don't retry a failed, timed-out, rejected, or unclear payment. a browser error, missing response, or completed `fill` doesn't tell you whether the merchant created an order or money moved. check the payment's events and the merchant's order record before you take another action.
</Warning>
