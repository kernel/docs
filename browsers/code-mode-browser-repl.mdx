Most browser agents get one tool per action: click, type, snapshot, drag. Every action is a model round trip, and multi-item work — "move every card", "fill every row" — becomes one call per item, with the model re-reading the conversation each time.

**Code mode** gives the model a single tool that runs code. The model writes a program that finds the elements it needs, acts on them, and checks the result, and the harness returns only what the program writes back. Loops, retries, and verification happen in code instead of in the conversation.

The [Browser REPL](/browsers/repl) is what makes code mode work for browser agents. It runs JavaScript in a persistent Node.js process on the browser's VM, so there's no CDP round trip from your machine, and top-level bindings survive across calls, so the model can define a helper once and reuse it for the rest of the task.

Code mode isn't tied to a particular agent framework. Any harness that can call tools can run it: give the model a browser REPL tool, keep the browser's lifecycle outside the loop, and make the REPL the only way the model controls the browser. This cookbook covers what that takes in any harness, then shows one working example: [AI SDK](https://ai-sdk.dev)'s [`ToolLoopAgent`](https://ai-sdk.dev/docs/reference/ai-sdk-core/tool-loop-agent) using the `browser_repl` tool from the [Kernel MCP server](/reference/mcp-server).

## The example task

The example runs the same task as [Using Playwright with Computer Use Fallback](/browsers/playwright-computer-use-fallback), against [magnitasks.com](https://magnitasks.com), a public Kanban-style board:

```
Go to magnitasks.com, navigate to Tasks, filter for Alice's tasks,
then drag every item card to the Done column.
```

In that cookbook, the Playwright `browser_drag` tool can't move a card: the board uses pointer-based drag-and-drop, which needs several intermediate `mousemove` events, so the agent hands off to computer use. In code mode, the model writes a drag with enough intermediate pointer movement itself, then runs it for every card.

## Tool calling vs. code mode

| | one tool per action | code mode |
| --- | --- | --- |
| a step is | one tool call and one model round trip | as many actions as the program contains |
| work over many items | one call per item | one loop or helper, reused |
| state between steps | the conversation | the conversation, plus REPL bindings such as helpers and cached lookups |
| checking a result | another tool call | part of the same program |
| what the model learns up front | a schema per tool | the REPL's helper API, from the tool description and instructions |

Code mode trades per-action control for fewer round trips. You no longer see each click as its own tool call, so the program has to verify its own work and write back what it changed.

## Adding code mode to any harness

Whatever harness you use — AI SDK, another agent framework, or your own loop over a model API — code mode needs the same pieces.

**A browser REPL tool.** The model's only browser tool takes a JavaScript cell and a session ID, runs the cell in the Browser REPL, and returns its output. You can get one of two ways:

| | Kernel MCP `browser_repl` | your own tool around `kernel.browsers.repl()` |
| --- | --- | --- |
| works with | any harness that can connect to an MCP server | any harness that can register a function tool |
| tool description | written by Kernel, and documents the REPL helpers and failure semantics | written by you |
| per-call time limit | up to 150 seconds | up to 300 seconds |
| comes with | the rest of the Kernel MCP tools, which you filter | only what you define |

Use the MCP tool when your harness speaks MCP: you get a maintained tool description and no tool code to write. Write your own tool when your harness can't connect to MCP servers, or when single cells need more than 150 seconds.

**A browser that lives outside the loop.** Create the browser before the agent runs, give the agent its session ID, and delete the browser when the run ends, in a `finally` block or its equivalent. The agent never creates or deletes browsers, so a run that fails or hits its step limit can't leak a session, and you can point the same agent at a browser from a [pool](/browsers/pools) or one with a [profile](/browsers/profiles).

**The REPL as the only control path.** Turn off tools that control the browser another way, such as Playwright execution and computer use, and tell the model in its instructions to rely on the REPL tool. Otherwise the model can slip back into one-action-per-call tools and you lose the point of code mode.

**A generous per-call budget, and no retries.** A timeout is destructive: it destroys the REPL and every helper the model defined, so give each call the most time the tool allows. And never let the harness or its HTTP client re-send a cell after a timeout or dropped connection — the first attempt may still be running, and a retry repeats its clicks and drags.

**Results the model can act on.** Return the cell's written output, errors with their stack, and any screenshots to the model as tool results rather than raising them as exceptions, so it can fix its code and try again. If a result says the REPL was terminated, the model needs to know its helpers are gone.

**Instructions that ask for programs.** Tell the model to inspect first, then write cells that complete a whole step and verify it, and to define reusable helpers at the top level. Without that nudge, models tend to send one action per cell, which gives back most of the round trips code mode saves.

## Example: AI SDK with the Kernel MCP server

This example uses AI SDK's `ToolLoopAgent` with OpenAI's `gpt-6-luna` at medium reasoning, and takes the REPL tool from the Kernel MCP server. Here's how it covers each piece:

- **Browser REPL tool:** `createMCPClient()` from `@ai-sdk/mcp` connects to `https://mcp.onkernel.com/mcp` over streamable HTTP, authenticating with your Kernel API key as a bearer token (see [MCP authentication](/reference/mcp-server/authentication)). `mcp.tools()` returns the server's tools, including `browser_repl`, as AI SDK tools.
- **Browser outside the loop:** `main()` creates the browser and starts a replay with the Kernel SDK, puts the session ID in the agent's instructions, runs `agent.generate()`, and deletes the browser in `finally`.
- **REPL as the only control path:** `activeTools` removes `execute_playwright_code` and `computer_action`, and the instructions tell the agent to rely on the built-in `browser_repl` tool and not to create or delete browsers.
- **Budget and retries:** the MCP `browser_repl` tool defaults to `timeout_sec: 60` and accepts at most 150, so the script wraps the tool's `execute` to run every call with 150 seconds. The MCP client's `maxRetries` defaults to `0` for tool calls, so a cell is never sent twice.
- **Results:** the MCP tool returns `success: false` with the error for syntax errors and exceptions, and the AI SDK MCP client passes screenshots from `repl.emitImage` to the model as image content.
- **Instructions:** the MCP tool's own description documents the REPL helpers, so the instructions only add the workflow and a few task-specific tips.

`ToolLoopAgent` runs the loop: it calls the model, runs the tool calls it makes, and feeds the results back until the model answers without calling a tool or the run reaches `isStepCount(25)`.

### Setup

```bash
npm install ai @ai-sdk/openai @ai-sdk/mcp @onkernel/sdk tsx
KERNEL_API_KEY=... OPENAI_API_KEY=... npx tsx code-mode-browser-repl.ts
```

The same `KERNEL_API_KEY` authenticates both the Kernel SDK and the MCP server. `@ai-sdk/openai` calls OpenAI directly with `OPENAI_API_KEY`. To use another provider, swap the `model` passed to `ToolLoopAgent`; the tools and the browser lifecycle don't change.

### The script

```ts code-mode-browser-repl.ts
import { createMCPClient } from "@ai-sdk/mcp";
import { openai } from "@ai-sdk/openai";
import Kernel from "@onkernel/sdk";
import { ToolLoopAgent, isStepCount, type ToolSet } from "ai";

const TASK_PROMPT =
	"Go to magnitasks.com, navigate to Tasks, filter for Alice's tasks, " +
	"then drag every item card to the Done column.";

// The Kernel MCP server's browser_repl tool accepts at most 150 seconds per call.
const REPL_TIMEOUT_SEC = 150;
// Agent steps before the loop gives up.
const MAX_STEPS = 25;
// Browser control goes through browser_repl, so the other control tools are turned off.
const DISABLED_TOOLS = new Set(["execute_playwright_code", "computer_action"]);

const instructions = (sessionId: string) => `You complete browser tasks in the Kernel browser session ${sessionId}.

Rely on the built-in browser_repl tool to control the browser. It runs JavaScript as a cell in a persistent Node.js REPL on the browser's VM. Pass session_id "${sessionId}" on every call. Don't create, update, or delete browsers; the session is already running and is cleaned up after you finish.

How to work:
1. Start by navigating and inspecting. Write back a compact summary of what matters (headings, buttons, inputs, and their text), not a raw dump.
2. After that, write programs, not single actions. One cell completes a whole step: it finds every element it needs, acts on each one, verifies the result, and writes back what changed. Prefer one cell that handles every item over one cell per item.
3. Define helpers you'll need again as top-level functions; they persist across cells. A top-level const or let can't be declared again in a later cell, so pick new names or use var.

Tips:
- js(fn, {arg}) returns JSON-serializable values only. DOMRects come back empty, so copy x, y, width, and height.
- For drag-and-drop, send cdp("Input.dispatchMouseEvent", ...): mousePressed, then ten or more mouseMoved events along the path, then mouseReleased.
- Each call can run for ${REPL_TIMEOUT_SEC} seconds. A timeout destroys the REPL and every binding in it.`;

async function main(): Promise<void> {
	const kernel = new Kernel();

	// The browser lives outside the agent loop: create it, hand the agent its session ID, delete it when the run ends.
	const browser = await kernel.browsers.create({ stealth: true });
	const replay = await kernel.browsers.replays.start(browser.session_id);
	console.log(`recording started: ${replay.replay_view_url}`);

	const mcp = await createMCPClient({
		transport: {
			type: "http",
			url: "https://mcp.onkernel.com/mcp",
			headers: { Authorization: `Bearer ${process.env.KERNEL_API_KEY}` },
		},
	});

	try {
		const tools: ToolSet = await mcp.tools();

		// Give every browser_repl call the full budget instead of the tool's 60-second default.
		const browserRepl = tools.browser_repl;
		tools.browser_repl = {
			...browserRepl,
			execute: (input: { code?: string }, options) => {
				console.log(`[browser_repl]\n${input.code ?? ""}`);
				return browserRepl.execute!({ ...input, timeout_sec: REPL_TIMEOUT_SEC }, options);
			},
		};

		const agent = new ToolLoopAgent({
			model: openai("gpt-6-luna"),
			reasoning: "medium",
			instructions: instructions(browser.session_id),
			tools,
			activeTools: Object.keys(tools).filter((name) => !DISABLED_TOOLS.has(name)),
			stopWhen: isStepCount(MAX_STEPS),
			onStepFinish: (step) => {
				for (const call of step.toolCalls) {
					if (call.toolName !== "browser_repl") console.log(`[${call.toolName}] ${JSON.stringify(call.input)}`);
				}
			},
		});

		const result = await agent.generate({ prompt: TASK_PROMPT });
		console.log(`finish reason: ${result.finishReason}, steps: ${result.steps.length}`);
		console.log(result.text);
	} finally {
		await mcp.close();
		await kernel.browsers.replays.stop(replay.replay_id, { id_or_name: browser.session_id });
		console.log(`replay ready: ${replay.replay_view_url}`);
		await kernel.browsers.deleteByID(browser.session_id);
	}
}

void main();
```

### What a run looks like

In three test runs, `gpt-6-luna` finished the task in 11 to 15 `browser_repl` calls. The early cells inspected the page through filtered accessibility snapshots, then opened **Filters** and selected Alice. A few calls failed and were fixed on the next try — for example, passing a bare `backendNodeId` number to `click()` instead of the node.

In the shorter run, the model imported `patchright` inside the REPL, as the tool description suggests, and moved both cards from one loop with Playwright's `dragTo()`, whose `steps` option sends the intermediate pointer movement the board needs:

```javascript
var taskTitles = ["Fix login authentication bug", "Fix mobile responsive issues"];
var doneColumn = pwPage.getByRole("heading", { name: "Done", exact: true }).locator("..").locator("..");
var dragResults = [];
for (var title of taskTitles) {
  var heading = pwPage.getByRole("heading", { name: title, exact: true });
  var card = heading.locator("../..");
  await card.dragTo(doneColumn, { targetPosition: { x: 160, y: 120 }, steps: 16 });
  await pwPage.waitForTimeout(600);
  dragResults.push({
    title,
    done: await doneColumn.getByRole("heading", { name: title, exact: true }).count(),
  });
}
repl.write(JSON.stringify(dragResults));
```

The `pwPage` binding came from an earlier cell, and the loop checked each card's new column before writing back. In another run, the model sent the drag as raw `cdp("Input.dispatchMouseEvent", ...)` events instead. Both approaches run inside `browser_repl`.

## Notes

- **Turning off Playwright execution doesn't remove Playwright.** The REPL ships `patchright` and `playwright-core`, and the model can import them in a cell. If you want the model to use only the native helpers, say so in the instructions.
- **Filter MCP tools you don't want the model to call.** In the example, `activeTools` only removes the two tools it lists. In two of three test runs, the model also checked `webmcp` for a site-provided action and, finding none, called `get_more_tools`, which reports a missing capability to Kernel. For tighter control, add names to `DISABLED_TOOLS` or build `activeTools` from an allowlist such as `["browser_repl"]`.
- **Writing your own REPL tool?** Call [`kernel.browsers.repl()`](/browsers/repl) with `timeout_sec` up to 300, set the SDK request timeout above `timeout_sec`, and turn off the SDK's retries for that call. The Kernel SDKs default to a 60-second request timeout with automatic retries, which would cut off a long cell and send it again.
- **Treat model-written code as untrusted.** The Browser REPL is [unrestricted code execution inside the browser VM](/browsers/repl#security-model), and page content can influence the code the model writes. Keep secrets you wouldn't hand to the page out of the VM's environment and filesystem.
- **Record the run.** The example wraps the agent run in `kernel.browsers.replays.start()` / `.stop()`, so every cell's effect lands on one replay video.
- **Other languages.** The example is TypeScript because AI SDK is TypeScript-only. The pattern carries over to any language: use the Kernel MCP server from a harness that supports MCP, or wrap the Python SDK's `kernel.browsers.repl()` as a tool.
